4. Apakah ini artefak baca file mock? (diuji; jawabannya: tidak memadai)
==============================================================================
`mockOrderCount()` (tests/test-consent-gate-e2e.mts:163) = panjang array di
ORDERS_FILE, file yang ditulis mock dengan `fs.writeFileSync` (truncate + write,
NON-atomik) pada setiap POST /v3/orders. Pembaca memang bisa melihat berkas
separuh, `JSON.parse` gagal, `mockOrders()` mengembalikan [], dan hitungannya
jadi 0 pada saat itu. Arah salahnya UNDERCOUNT — bukan overcount.
Gejala asli OVERCOUNT (+2), dan overcount itu dikonfirmasi dua sumber yang TIDAK
menyentuh file itu:
  * baris `checkout_claims` kedua benar-benar ada dan berstatus 'created'
    (bukan 'failed'/sisa klaim),
  * dua order_id berbeda muncul di respons HTTP (dihitung in-memory).
Kalau hitungan file yang salah, tidak mungkin ada baris klaim kedua di DB.
Jadi "hitungan file meleset" BUKAN penjelasan untuk merah 01:18.

Yang tetap benar dan layak diperbaiki (higienitas, tests/ saja — usul §6):
tulisan mock non-atomik + tidak ada penanda "file ini milik run mana".
Kelas masalah yang nyata untuk itu: dua run dengan prefix /tmp (atau DB) yang
sama ⇒ dua mock menulis file yang sama (mock menulis `[]` saat start lalu array
penuhnya tiap POST), dan pembaca tidak bisa membedakan order milik run mana.
Isolasi RX2-2 (DB/port/prefix per-worktree) menutup kelas itu; di run 01:18
isolasi DB-nya memang di-override bersama (`HARNESS_PG_DB=thrivin_shared_sim`).
