1. Bug + fix (opsi i yang disarankan kartu)
==============================================================================
Akar masalah: cabang replay (langkah 2 di claim_checkout_order) menyamakan
status='failed' dengan "percobaan sebelumnya gagal sebelum order tercetak".
Padahal 'failed' lahir dari DUA jalur:
  (a) release_checkout_claim (order_id NULL — aman di-grant ulang), dan
  (b) retire 3b: baris 'created' belum dibayar > TTL 60 menit → 'failed',
      order_id/payment_url TETAP terisi dan link Scalev-nya masih bisa dibayar.
Jalur (b) di-replay → di-grant ulang → route mencetak order KEDUA.

Fix (staging/schema-consent.sql, langkah 2):
  +  IF v_existing.order_id IS NOT NULL THEN
  +    RETURN json_build_object('status','already_created',
  +      'claim_id', v_existing.id,
  +      'order_id', v_existing.order_id,
  +      'payment_url', v_existing.payment_url);
  +  END IF;
  (baris 'failed' TANPA order tetap dipakai ulang seperti sebelumnya)
Signature claim_checkout_order TIDAK berubah (hindari overload PostgREST, RX2-2).
3b sengaja TIDAK mengosongkan order_id (opsi ii ditolak: mengosongkan di situ justru
membuka jalur grant ulang — bertabrakan dengan keputusan owner "kunci sama = order sama").
Route `create-order` sudah menangani `already_created` (balas order/link yang sama,
`replay: true`, tanpa panggilan Scalev) — nol perubahan src/, jadi nol perubahan build.
tests/harness/migrations/006-consent-gate.sql = salinan otomatis dari staging/ oleh
seed.sh; ikut di-commit dan diverifikasi byte-identik (`diff` bersih).
