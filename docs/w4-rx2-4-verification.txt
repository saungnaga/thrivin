2a. Kenapa urutan SIGTERM-vs-cabut-pipe itu penting (kalau tidak: kebalikan R2)
==============================================================================
Percobaan A (`/tmp/rx24-diag-kill-order-first.log`) — SIGTERM dulu, pipe stderr TIDAK
dicabut:
  up, pid=3194518 / SIGTERM ke grup -pid / exitCode sesudah 2s: 0
Percobaan B (`/tmp/rx24-diag-destroy-first.log`) — `stderr.destroy()` DULU, baru SIGTERM:
  stderr destroyed; SIGTERM ke grup / MASIH HIDUP sesudah 3s  (hanya SIGKILL yang mematikan)

Makanya `stop()` baru mencabut pipe di grace 1,5 s, bukan sebelumnya. Kalau ini dilanggar,
perbaikan R2 berubah jadi kebocoran baru: stack "normal" pun tidak mati saat stop().

4. MODE YANG TIDAK DIDUKUNG (R4) — WAJIB dibaca sebelum menjalankan gate
==============================================================================
- SATU worktree = SATU run pada satu waktu. Dua `run-all.sh` (atau dua suite e2e) sekaligus
  dari worktree yang SAMA sekarang ditolak di muka oleh lock; sebelum lock ada, run kedua
  gagal jauh di dalam `seed.sh` (DDL bersamaan di DB yang sama, exit 1) — Sentinel sudah
  memprobe ini: run1 gagal keras, run2 128 PASS.
- Dua worktree paralel tetap didukung (nilai DB/port/prefix diturunkan dari path worktree).
- Tabrakan PORT_BASE antar worktree (~1/1200) dulu bisa senyap; sekarang gagal keras dengan
  pesan identitas (R3). Jalan keluar: set HARNESS_PORT_BASE / HARNESS_PG_DB eksplisit.

5. Status & batasan
==============================================================================
- Nol apply Supabase/staging/produksi; `staging/*.sql` tak tersentuh; `src/` nol perubahan.
- Perubahan perilaku yang DISENGAJA (semuanya gagal-keras, bukan gagal-senyap):
  * mock tanpa port -> exit 2 (sebelumnya diam-diam 4111);
  * listener asing di port proxy/mock -> throw (sebelumnya diadopsi);
  * sisa proses/port dari run lain tidak lagi diadopsi (RUN_ID beda) -> throw;
  * run kedua dari worktree sama -> ditolak lock sebelum seed.
- Sisa yang BELUM: `HARNESS_RUN_ID` manual bisa "mengakui" run lain sebagai milik sendiri
  (kalau di-set eksplisit sama); itu memang jalur override yang disengaja.
- `flock` tidak tersedia -> lock dilewati (dicatat di kode, bukan gagal diam-diam).

6. Catatan jujur
==============================================================================
- Klaim di `report.md:375` dan §1 dokumen RX2-2/3 ("default 4111 sudah hilang") SEBELUM
  kartu ini hanya benar untuk port suite, bukan untuk mock yang dijalankan manual —
  `mock-scalev.mjs:17` masih memegang fallback 4111. Sesudah R1 fallback itu benar-benar
  hilang, dan guard permanen mengeceknya (termasuk fetch ke 4111 harus ECONNREFUSED).
- R2 "pemanggil menggantung" itu nyata tapi berbatas: yang menggantung adalah proses
  pemanggil yang stderr pipe anaknya masih hidup. Perbaikannya = kill-dulu-baru-cabut
  (§2a), bukan sekadar menambah try/catch.
- Yang TIDAK diklaim: tidak ada uji dua-worktree-paralel ulang di ronde ini (itu kriteria
  RX2-2 yang sudah dibuktikan; perubahan ronde ini tidak menyentuh penghitungan
  DB/port/prefix per-worktree). Batas jujur: gerbang utama ronde ini adalah gate satu
  worktree (§3d) + probe identitas.
