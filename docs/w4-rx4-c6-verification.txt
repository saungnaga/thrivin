1. Akar + fix
==============================================================================
`staging/schema-webhook-onboarding.sql:94-96` membuat fungsi maintenance dengan

  DROP FUNCTION IF EXISTS purge_expired_webhook_data();
  CREATE OR REPLACE FUNCTION purge_expired_webhook_data() ... ;

**tanpa GRANT/REVOKE eksplisit**. Fungsi itu menghapus baris (`webhook_events_inbox`,
`onboarding_snapshots`) dan menulis `purge_audit_log`. ACL-nya karena itu bukan milik
berkas, melainkan milik role yang meng-apply:

  (a) apply PERTAMA — fungsi baru Postgres default EXECUTE ke PUBLIC, jadi `proacl` NULL
      dan `has_function_privilege('anon', …)` = **true** sejak detik pertama;
      diukur: proacl = <NULL>, anon=true, authenticated=true.
  (b) apply ULANG — role apply yang punya `ALTER DEFAULT PRIVILEGES … GRANT ALL ON
      FUNCTIONS TO anon, authenticated` (perilaku Supabase, dimodelkan harness di
      tests/harness/migrations/003-harness-grants.sql:22) menambahkan entri eksplisit:
      diukur: {=X/postgres,postgres=X/postgres,anon=X/postgres,authenticated=X/postgres}.
  (c) `DROP` di (94) membuat setiap apply ULANG me-reset ACL ke default ⇒ bocor (b)
      kembali walau pernah dipaku manual di DB.

Catatan akurasi klaim (pola C-1): kartu menyebut bocornya lewat "seed kedua / default
privileges". Itu benar tapi BUKAN satu-satunya jalur — jalur (a) sudah cukup, dan itu
sebabnya asersi suite ini juga berlaku untuk apply pertama. Kedua jalur dibuktikan di §2.

=== Fix (2 baris + komentar, di berkas yang sama dengan DDL-nya) ===
  REVOKE ALL ON FUNCTION purge_expired_webhook_data() FROM PUBLIC, anon, authenticated;
  GRANT EXECUTE ON FUNCTION purge_expired_webhook_data() TO service_role;

Preseden: pola identik di `staging/schema-consent.sql` (baris 1168-1206) dan
`staging/schema-promo-codes.sql` (459-472), di mana setiap RPC di-REVOKE dari
PUBLIC/anon/authenticated lalu di-GRANT ke service_role.
Alasan `GRANT` eksplisit ke service_role: setelah `REVOKE … FROM PUBLIC`, hak warisan
hilang — tanpa GRANT, jalur ops (service_role) kehilangan EXECUTE.
pg_cron tidak terpengaruh: ia menjadwalkan `SELECT purge_expired_webhook_data()` sebagai
role yang men-schedule (superuser), bukan sebagai anon/service_role.

Fungsi lain di berkas yang sama: NOL (`grep -c 'CREATE OR REPLACE FUNCTION'
staging/schema-webhook-onboarding.sql` = 1, dan itu fungsi ini). View di berkas itu
(`v_webhook_retention_backlog`) sudah dipaku REVOKE/GRANT sejak awal (baris 148-149).

4. Sapuan kelas — objek lain yang masih EXECUTE untuk anon (diukur, bukan diasumsikan)
==============================================================================
Di DB harness pasca-fix (`seed.sh --fresh` + re-apply):

  SELECT oid::regprocedure, proacl FROM pg_proc
   WHERE pronamespace='public'::regnamespace AND prokind='f'
     AND has_function_privilege('anon', oid, 'EXECUTE');

  * fungsi ekstensi (pgcrypto: crypt/armor/digest/pgp_* …) — `proacl` NULL = EXECUTE
    warisan PUBLIC. Bukan objek aplikasi, nol baris aplikasi yang dibaca/dihapus
    lewatnya; di Supabase pgcrypto hidup di schema `extensions`. TIDAK diubah di kartu ini.
  * `consent_events_block_mutation()` — TRIGGER function, ACL memuat `=X/postgres` +
    anon/authenticated. Tidak ada jalur eksploitasi: dipanggil sebagai fungsi biasa
    selalu ERROR — diukur: `SELECT public.consent_events_block_mutation();` ⇒
    `ERROR: trigger functions can only be called as triggers` (prorettype = `trigger`,
    jadi PostgREST juga tidak mengeksposnya). SENGAJA tidak diubah di kartu ini:
    memperbaikinya melebar ke `staging/schema-consent.sql` (diff kartu lain yang masih
    di-review). Dicatat sebagai kandidat higiene, bukan risiko.
  * fungsi `purge_expired_webhook_data()` — TIDAK ada lagi di daftar ini (inti kartu).

`DROP FUNCTION` lain di staging/: hanya `redeem_promo(...)` di
`staging/schema-promo-codes.sql:180`, dan signature hasil DROP-nya sudah di-REVOKE/GRANT
di baris 459+ (nol temuan tambahan).
