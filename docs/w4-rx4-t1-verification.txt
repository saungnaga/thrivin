1. Akar + fix (pilihan yang diambil dan alasannya)
==============================================================================
Akar (bukan dugaan — Sentinel sudah membuktikannya deterministik, dan mekanismenya
direproduksi ulang di asersi di sini): langkah 6
  SELECT ... FROM checkout_claims WHERE ... status='created' AND paid_at IS NULL
dan langkah 7
  INSERT INTO checkout_claims (...) VALUES (..., 'in_flight')
ada di snapshot READ COMMITTED yang BERBEDA di dalam satu transaksi. Kunci advisory
hanya menjaga transaksi KLAIM: panggilan Scalev + complete_checkout_claim milik
request pertama jalan di transaksi lain. Kalau commit `complete` itu menyelip di
antara langkah 6 dan langkah 7 milik request kedua:
  * langkah 6 tidak melihat baris 'created' (saat itu masih 'in_flight'), dan
  * langkah 7 tidak ditahan `uq_checkout_claims_inflight_phone`
    (`WHERE status='in_flight'`) karena baris pertama SUDAH BUKAN in_flight lagi.
=> request kedua `granted` => route mencetak order kedua yang juga bisa dibayar.

Fix yang dipilih: **unique partial index yang juga menjaga baris hidup 'created'**
(staging/schema-consent.sql, blok §4), dipasang dalam SATU transaksi dengan urutan
CREATE dulu / DROP belakangan (follow-up F-1, bagian 6):
  BEGIN;
  CREATE UNIQUE INDEX IF NOT EXISTS uq_checkout_claims_live_phone
    ON checkout_claims (tenant_id, phone)
    WHERE status IN ('in_flight', 'created') AND paid_at IS NULL;
  DROP INDEX IF EXISTS uq_checkout_claims_inflight_phone;
  COMMIT;

Alasan memilih index (bukan re-check + INSERT di bawah kunci yang sama):
- Penjaganya jadi sifat DB, bukan urutan baca-tulis di plpgsql: tidak ada lagi
  "baca dulu" yang bisa ketinggalan snapshot. INSERT ditahan index sampai transaksi
  yang mengubah baris itu commit, lalu langsung `unique_violation` — ditangkap blok
  EXCEPTION yang SUDAH ADA di langkah 7 (`in_flight` -> route 409 ORDER_IN_FLIGHT).
- Nol perubahan badan fungsi, nol perubahan `src/`, kontrak sukses
  (`already_created` / `reuse_unpaid` / `granted`) tidak disentuh.
- Alternatif re-check + ROLLBACK membawa risiko yang tidak perlu: ROLLBACK di tengah
  transaksi membatalkan juga UPDATE retire 3/3b dan INSERT-nya sendiri, dan pola
  "INSERT lalu cek apakah ada baris lain" rentan deadlock dua arah kalau dua sesi
  sama-sama memegang barisnya. Index menyerahkan urutan itu ke penguncian baris
  standar Postgres (penunggu tidak menahan apa pun).

Detail yang penting:
- `paid_at IS NULL` ada di predikat karena pembelian ULANG setelah lunas harus tetap
  boleh (mark_checkout_claim_paid mengisi paid_at -> baris keluar dari index), dan
  baris yang sudah di-retire 3b (`status='failed'`) juga keluar. Keduanya dijaga
  asersi (lihat bagian 2c), bukan asumsi.
- Nama index DIGANTI + `DROP INDEX IF EXISTS` yang lama, bukan
  `CREATE ... IF NOT EXISTS` dengan nama lama. Alasan: seed.sh dan apply ke staging
  menjalankan ulang file ini ke DB yang SUDAH ada; nama yang sama + IF NOT EXISTS
  akan diam-diam mempertahankan index lama yang sempit (lubang tetap terbuka) dan
  membuat "migrasi sukses" itu palsu. Bukti pg_indexes di bagian 2d + 3.
- Batas: index UNIQUE per (tenant_id, phone) — kalau di DB mana pun sudah ada DUA
  baris hidup untuk satu nomor (mis. hasil race ini di produksi), CREATE INDEX akan
  GAGAL. Untuk staging/produksi itu keputusan ops (bagian 5).

5. Batasan & catatan jujur
==============================================================================
- UNIQUE index ini mensyaratkan DB yang di-apply TIDAK sedang memuat dua baris hidup
  untuk satu nomor. Kalau pernah terjadi di staging/produksi, CREATE INDEX akan gagal
  (by design: lebih baik gagal keras daripada index-nya diam-diam tidak ada). Deteksi
  + pembersihan data = keputusan ops.
  LANGKAH OPS WAJIB SEBELUM APPLY (pre-check duplikat, F-1 poin 4) — jalankan dulu ke
  DB target; ADA baris keluaran = CREATE-nya memang akan gagal, jangan dipaksa:
    SELECT tenant_id, phone, count(*) FROM checkout_claims
     WHERE status IN ('in_flight','created') AND paid_at IS NULL
     GROUP BY 1,2 HAVING count(*) > 1;
  Kalau ada hasil, bersihkan/retire barisnya dulu (keputusan ops, lihat
  data-cleanup-plan) lalu apply ulang. `CREATE INDEX` non-concurrent memegang
  ACCESS EXCLUSIVE sebentar -> apply saat trafik rendah (aturan baris apply ada di
  §4 file skema, blok BEGIN/COMMIT).
- `staging/schema-consent.sql` masih DRAFT dan staging masih memuat badan fungsi
  pra-fix; apply ke staging/produksi adalah keputusan ops terpisah (dan wajib
  delta-review ulang Sentinel untuk jalur uang ini sebelum merge/deploy).
- Nol perubahan `src/`: route `create-order` sudah membalas 409 ORDER_IN_FLIGHT untuk
  `in_flight`, dan tidak ada kontrak sukses yang disentuh. Asersi e2e memaku kode 409
  itu supaya tidak diam-diam berubah jadi kode lain.
- Residual T5 dari review 4 masih terbuka dan BUKAN milik kartu ini: link Scalev lama
  tetap hidup setelah retire TTL (lingkup F-W4-1c, kartu atlas t_16dd8537).
- Flaky pra-ada "dua kunci berbeda paralel" (1 dari 6 run merah, dilaporkan Sentinel)
  kini punya penjaga deterministik di level DB + 5 run e2e hijau berturut-turut.
  Klaim yang jujur: yang dibuktikan adalah celah snapshot-nya tertutup; flaky HISTORIS
  itu sendiri tidak pernah diklaim sebagai satu-satunya penyebab merah.

(`psql -v ON_ERROR_STOP=1 -f -`, autocommit lewat seed.sh). Urutan lama (DROP dulu,

sama sekali, dan apply utuh berhenti sebelum §5 (semua RPC + grant). Kegagalan apply
justru meninggalkan DB LEBIH LEMAH dari sebelum apply — "gagal keras" != fail-safe.
